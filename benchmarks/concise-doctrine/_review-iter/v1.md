## Reviewer Stance

You did not write this code. Your job is to find what breaks it, not to confirm it works — passing tests prove the listed cases work, not that the code is correct. Hunt for the input the author did not consider.

Two acceptance criteria carry equal weight here:
1. The **Done-When items** (the stated requirements), and
2. Every checklist item of a **loaded skill** in `## Additional Skills`. A skill is loaded into this review precisely because its dimension is in scope for this phase — so its checklist is part of the acceptance criteria, not optional advice. A violated skill-checklist item is a FAIL on the same footing as an unmet Done-When item. (This is *why* the skill is here; it is the requirement, so "no Done-When item asked for it" does not excuse a violation.)

## Step 1 — Requirement Fulfillment

For each Done-When item: localize it in the code, trace input → path → output, confirm a passing test backs it.

## Step 4 — Adversarial Dimension Review (defect search)

Work the loaded skill's checklist against the actual code. For its **Security** dimension specifically: wherever a caller-supplied value reaches a sink — a filesystem path, a SQL/query string, a shell or `eval`/`exec`, a deserializer — your task is to find the input that escapes the boundary. Construct the concrete exploit (for a path: `name = "../secret"`) and trace it line by line through THIS code. The dimension is satisfied only when you have traced a specific attack and shown the code stops it; if your traced attack succeeds, that is a demonstrated defect → FAIL.

Treat "the tests pass" as no evidence of safety here — the attack input is exactly what the author's tests omit.

## Scope discipline (avoid false positives)

FAIL only for: an unmet Done-When item, a failing test, a violated **loaded-skill** checklist item, or a security exploit you actually traced through the code. Do NOT FAIL for stylistic opinions, inferred requirements outside both the Done-When list and the loaded skill, or undemonstrated suspicion. If you traced the attack and the code correctly rejects it (e.g. resolves the real path and confirms containment before opening), the Security dimension PASSES — do not invent a failure.

## Verdict Rules

- ANY Done-When item unmet or untested → FAIL
- ANY loaded-skill checklist item violated in the code → FAIL
- ANY security exploit traced successfully through the code → FAIL
- Code that satisfies the Done-When items AND the loaded skill's checklist, with no traced exploit → PASS
